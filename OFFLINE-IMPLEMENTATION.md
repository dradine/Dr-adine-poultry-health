# Adine Offline Mode — Implementation and Release Gate

## Scope
This branch adds an offline foundation for previously verified users, local creation of farms/houses/flocks, daily broiler and layer monitoring, weekly monitoring, and new accounting transactions. Reports and analysis remain online. Layer weekly/monthly aggregates remain generated by the existing period engine after daily records synchronize; they are not manually fabricated offline.

## Data-flow rules
1. The user must have signed in successfully online on this device at least once. A first-ever account/device cannot be verified with no connection.
2. The offline grant is stored for at most 7 days after the last successful online profile validation. No password or service-role key is stored.
3. Form records are persisted to IndexedDB before the UI reports success.
4. Offline resume is enabled only for farm-operator/farm-manager accounts; signing out clears cached offline grants but deliberately retains queued records.
5. Every locally created record gets a stable UUID. The sync queue uses upsert-on-id with ignoreDuplicates to tolerate a server commit whose response was lost.
6. Farm → house → flock → monitoring dependencies are sent in queue order; a child is held while its parent remains pending.
7. A server/RLS/constraint rejection leaves the item on-device and marks it for review. It is not silently deleted.
8. A user can export pending operations to JSON and restore them only while signed into the same user ID.
9. Existing synced records are intentionally not edited or deleted offline in v1. New records and edits to still-pending local records are supported.
10. Reports, standards comparisons, and central analytics remain online. Layer monthly/weekly aggregates continue to be produced by the existing online engine.

## Browser storage
- IndexedDB stores the profile minimum, authorized snapshots, local records, and queue.
- Service Worker caches app shell and static dependencies, never Supabase REST/Auth/Storage/realtime responses.
- The app requests persistent storage where supported and warns when the browser has not granted it. This reduces, but cannot eliminate, browser eviction or device-loss risk.
- The backup file contains farm/financial data. Users must store it securely and avoid sending it to unauthorized people.

## Security
- Offline access is a convenience grant, not a replacement for server authorization.
- The server/RLS remains authoritative at synchronization time.
- If a user's permission is revoked while offline, the device cannot know until it reconnects. The server may reject queued writes; rejected records remain local for review.
- Do not add service_role credentials or store passwords in IndexedDB.
- Cached data is not encrypted by this browser-only implementation. Protect devices with a passcode and avoid shared/unlocked devices.

## Known v1 limitations
- A never-before-used device needs internet for first login and for initial app asset download.
- A page/form must have been cached by a successful online visit or by the shell cache. Dynamic third-party resources not listed in the service worker still require a first online load.
- Offline access is limited to 7 days from last successful profile validation.
- Offline edits/deletes of already-synchronized records are blocked to avoid lost-update conflicts.
- A stale offline snapshot may be out of date. All writes are re-authorized by Supabase when synchronized.
- Layer monthly and derived layer-weekly records are rebuilt by the existing online period engine; they are not generated as authoritative reports while offline.
- A backup export is for pending operations only, not a full database export.

## Automated browser smoke test
- GitHub Actions runs `tests/offline-browser-smoke.cjs` with Playwright/Chromium against a local HTTP server on `127.0.0.1`. Localhost is treated as a secure context by modern browsers, so this validates service-worker behavior without publishing the app or changing production hosting.
- The smoke test checks that the service worker controls the login page, login/dashboard/offline fallback pages are cached, IndexedDB is available, cached login navigation still renders with browser networking disabled, and Supabase API URLs are not stored in the service-worker cache.
- Behavioral checks cover complete-vs-truncated snapshot reconciliation, scope-limited stale-row removal, preservation of another flock's cached history, offline persistence of farm → house → flock → daily monitoring records, ordered synchronization, and idempotent retry after simulating a server-accepted insert whose network response was lost. Sync uses an isolated in-browser mock server; it does not write to the production Supabase project.
- `tests/offline-auth-policy.test.cjs` runs 10 behavioral cases against the actual `auth.js` policy, including boolean/string/numeric inactive flags, pending/suspended/revoked access, legacy active profiles, and owner-role bypass prevention.
- This is a desktop Chromium simulation, not a real iOS Safari/Android Chrome device test and not a publicly hosted HTTPS staging environment. It does not validate real Supabase authentication/RLS policies or actual device storage eviction. Those checks remain required before production rollout.
- To provide a public HTTPS staging URL, use a separately configured staging host/project with its own credentials and no production-domain/Pages-setting changes. Do not point the production custom domain at this branch for testing.

## Release checklist — must pass on real devices before production rollout
### Install and startup
- [ ] Visit online once, sign in, confirm service worker is active and shell/CDN dependencies are cached.
- [ ] Close/reopen on iPhone Safari/PWA and Android Chrome; enable airplane mode.
- [ ] Confirm login page opens and the offline-resume button is available only for a valid previously verified account.
- [ ] Confirm a fresh/never-verified device cannot bypass authentication offline.

### Farm hierarchy
- [ ] Create farm offline; reload; verify it remains visible.
- [ ] Create house for that farm offline; reload; verify relation.
- [ ] Create flock for that house offline; reload; verify relation.
- [ ] Reconnect; confirm farm, house, flock appear exactly once and IDs/FKs are preserved.
- [ ] Force parent sync failure; verify child writes remain queued.

### Monitoring
- [ ] Create broiler daily record offline; reload; verify record and totals.
- [ ] Create layer daily record offline; reload; verify date selection and history.
- [ ] Create weekly record offline; verify duplicate week/age is blocked.
- [ ] Reconnect; verify daily and weekly rows are present exactly once.
- [ ] Verify layer weekly/monthly aggregates update when the existing online reports/period engine runs.
- [ ] Verify existing synced record edits/deletes are blocked offline rather than falsely reported as saved.

### Accounting
- [ ] Create income and expense offline; reload; confirm totals and profit/loss calculations.
- [ ] Reconnect; verify each transaction appears once on the server.
- [ ] Verify existing synced transaction edits are blocked offline.
- [ ] Verify financial totals match server results after synchronization.

### Failure and recovery
- [ ] Drop connection during an upload; verify the item remains queued and retry is idempotent.
- [ ] Test RLS/constraint rejection; verify status says review required and the item is retained.
- [ ] Export a pending backup; sign in as the same user on another device and restore; verify only that user's operations are accepted.
- [ ] Attempt to restore a backup under a different user; verify rejection.
- [ ] Simulate storage quota failure; verify the form is not cleared and the UI explicitly says local saving failed.
- [ ] Test app update with pending records; verify database migration does not erase them.
- [ ] Test current and previous iOS Safari plus Android Chrome.
- [ ] Verify no regression to existing online reports, calculations, standards, or broiler/layer separation.
